# Zicsr 拓展与 CoreMark 运行相关 CSR 寄存器指南

### 一、 完整的 Zicsr 拓展说明

在 RISC-V 最新规范中，**Zicsr 拓展本身并不强制要求你实现特定数量的 CSR 寄存器**。Zicsr 扩展的核心是将所有 CSR 访问指令（如 `csrrw`、`csrrs` 等）独立出来，并为架构定义了一个 12 位（12-bit）的地址空间，这意味着硬件最多可以支持 4096 个 CSR。

你的 CPU 实际上需要实现哪些具体的 CSR，完全取决于你所处的**权限模式（Privilege Mode）**。

### 二、 基础机器模式（M 模式）需实现的核心 CSR

如果你实现的是处于“级别 1：纯裸机微控制器”的默认情形（仅支持 M 模式），为了保证硬件系统的完整性（例如异常和中断处理），除了硬件计时器外，你还需要额外支持以下核心 CSR：

* **`mstatus`**：全局状态寄存器。
* **`mtvec`**：异常入口基址寄存器。
* **`mepc`**：记录发生异常时的 PC（程序计数器）值。
* **`mcause`**：记录异常发生的原因。

### 三、 运行 CoreMark 需要支持的 CSR 列表及其读写属性

CoreMark 作为一个 Benchmark 测试，最核心的需求是能够进行“计时”，以便计算出 CoreMark/MHz 的跑分成绩。因此，它强依赖于硬件内部的周期计数器或实时时钟寄存器。

对于早期的裸机验证和 CoreMark 运行，你需要重点实现以下 Machine Mode（机器模式）下的性能监控寄存器：

| 寄存器名称 | 地址 | 功能描述 | 读写属性 | 是否为 CoreMark 必需 |
| --- | --- | --- | --- | --- |
| **`mcycle`** | `0xB00` | 机器模式周期计数器（低 32 位）。 | **可读可写** | **是** |
| **`mcycleh`** | `0xB80` | 机器模式周期计数器（高 32 位）。由于 RV32I 下 32 位极易溢出，需与低位拼成 64 位计数器。 | **可读可写** | **是** |
| **`minstret`** | `0xB02` | 退休指令计数器（低 32 位）。 | **可读可写** | 否（但强烈建议加入，用于测算微架构的 IPC 指标） |
| **`minstreth`** | `0xB82` | 退休指令计数器（高 32 位）。 | **可读可写** | 否（但强烈建议加入，用于测算微架构的 IPC 指标） |

#### 针对这些 CSR 的读写行为逻辑与避坑点：

1. **可读可写属性**：在这些地址的高位划分中（如 `0xB00`），包含了权限与读写属性信息，这就意味着逻辑上它们是支持软件层面进行读取和写入的。
2. **硬件自发行为**：即使没有指令操作，这几个性能监控寄存器也会自发工作。例如 `mcycle` 会在每一个时钟周期的上升沿无条件加 1；`minstret` 会在流水线写回（WB）阶段，每成功完成一条指令且未发生异常时加 1。
3. **软件干预修改**：你可以通过 `csrrw` 这样的指令，将通用寄存器的值直接覆盖原 CSR 的值进行写入；也可以通过 `csrrs` 或 `csrrc` 进行按位的置位与清零运算。
4. **纯读操作警告**：当使用 `csrrs` 或 `csrrc` 指令，且源寄存器被指定为零寄存器 `x0` 时，你必须将其视为纯粹的读指令，此时硬件**绝对不能**对目标 CSR 开启写使能。CoreMark 移植层调用的内联汇编正是通过这种伪指令形式来读取计数值的。
