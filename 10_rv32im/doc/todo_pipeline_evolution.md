# 流水线架构演进 TODO：Valid 气泡机制重构

**Author**: Antigravity | Gemini 3.1 Pro High
**Date**: 2026-06-26

## 1. 背景与当前缺陷

目前，我们在处理流水线气泡（如 Cache 延迟引起的无效数据）和异常控制（如分支预测失败引起的 Flush）时，采用了“强制塞入物理 NOP 指令 (`32'h00000013`)”的策略：
- `ifu.sv` 中使用 `if_valid ? instr : NOP` 屏蔽复位或跳转当拍的无效 SRAM 数据。
- `idu.sv` 中使用 `flush -> 写入 NOP` 抹除已进入 ID 级的错路径指令。

这种做法在当前的简单 5 级标量流水线中能正常跑通，但面向未来的高性能架构（如引入 I-Cache、多发射、乱序执行）时，存在以下严重问题：
1. **功耗与资源浪费**：物理 NOP 依然是一条真实指令，它会穿过译码级、占用发射队列 (Issue Queue) 表项，最终消耗 ALU 的加法计算资源。
2. **解耦极其困难**：当引入 I-Cache 导致取指延迟变为不定长（Cache Miss）时，基于全局 stall 塞 NOP 的控制逻辑会变得极其臃肿和脆弱。

## 2. 演进目标

废弃基于“物理 NOP”的强制指令覆写机制，彻底转向标准的、基于“有效位 (`valid`)”的数据流传递机制。

## 3. 改造步骤 TODO

### [ ] Step 1: 全流水线引入 Valid 寄存器
在 IF/ID、ID/EX 等各级流水线级间寄存器中，额外增加 1-bit 的 `r_valid` 状态位，伴随指令数据一路传递。

### [ ] Step 2: 改造 IFU (Fetch Unit)
- 取消 `ifu.sv` 内部 `if_valid ? i_if_instr : NOP` 的掩码逻辑。
- IFU 仅向外输出 `o_if_valid`（指示从 SRAM 读出的当前数据是否有效）。即使当前 SRAM 吐出的是垃圾数据，也不做修改，直接通过 `valid=0` 标识其为垃圾。

### [ ] Step 3: 改造 IDU (Decode Unit) 与 Flush 控制
- `idu.sv` 接收上一级的 `valid` 位。
- **关键修改**：当收到全局 `flush` 信号（分支跳转）时，**直接将当前级的 `r_valid` 清零**，不再覆写 `r_instr_id` 为物理 NOP。任由错路径的垃圾指令留在寄存器中，但由于 `valid=0`，它变成了“幽灵”。

### [ ] Step 4: 改造后级执行与控制 (EX / MEM / WB)
- 流水线后级的一切活动（译码、ALU 计算、访存、写回）必须以 `valid == 1` 为绝对前提。
- 当检测到流水级输入的 `valid == 0` 时，关闭一切状态更新（禁止写 RF、禁止写 Memory），并在物理实现时可引入时钟门控 (Clock Gating) 进一步降低功耗。

## 4. 架构意义

完成此改造后，IFU 和 IDU 之间将被彻底解耦。IFU 可以无缝外接 Fetch Queue（取指队列），多发射架构下也只需为每个指令槽单独增加一个 Valid bit 即可实现细粒度的指令废弃控制，不再受限于全局暴力的 Flush 逻辑。
