# UART 串口发送（uart_tx）软硬件协同机制分析

本程序（`tests/programs/uart_tx/main.c`）是一个经典的串口控制与调试打印示例。在您的 RISC-V SoC 硬件上运行时，它通过极简的 C 代码调用，一步步转换并触发物理引脚（`TX`）的电平翻转。

以下是该程序的**底层反汇编代码映射关系**与**核心物理硬件行为**的深度解析。

## 二、 核心函数 1：`uart_init()` 如何映射并激活硬件？

在 `main` 函数中，首步执行 `jal ra, 820` 跳转到 `uart_init` 执行。

### 1. 对应反汇编与执行细节
```assembly
00000820 <uart_init>:
  ...
  82c:	300007b7          	lui	a5,0x30000
  830:	00300713          	li	a4,3
  834:	00e7a023          	sw	a4,0(a5)       # 物理地址 0x30000000 写入 3
  
  838:	100007b7          	lui	a5,0x10000
  83c:	00000737          	lui	a4,0x0
  840:	7d470713          	addi	a4,a4,2004     # 合成地址 0x7d4，即 uart_putc 首地址
  844:	06e7aa23          	sw	a4,116(a5)     # 写入 RAM 的 xfunc_out (0x10000074)
  ...
```

### 2. 对应的硬件行为
1.  **激活硬件发送/接收模块**：
    汇编指令 `sw a4, 0(a5)` 向芯片物理外设地址 **`0x30000000`**（串口控制器 `CTRL` 寄存器）写入数值 **`3`**。
    *   **SoC 内部硬件动作**：总线接口模块检测到对串口基地址的写周期，把 `CTRL` 寄存器更新为二进制 `2'b11`。
    *   **外设物理行为**：串口控制器内的 `tx_en`（发送使能）和 `rx_en`（接收使能）端口立即被拉为**高电平**，分频计数器和波特率发生器开始工作，发送引脚（`TX`）被强制拉为高电平闲置状态。
2.  **挂载软件驱动网关**：
    汇编指令将物理函数指针 `0x7d4`（`uart_putc` 的指令起始地址）写入了 RAM 数据区的全局函数指针变量 `xfunc_out`（地址 `0x10000074`）中。这相当于完成了软件接口的动态路由注册。

## 三、 核心函数 2：`xprintf("hello world\n")` 五级跳物理调用链

当主程序调用 `xprintf` 时，数据从只读 Flash 经过层层函数跳转，最终转换成物理引脚的串行电平输出。其**五级跳级联调用链**如下：

```
 ┌──────────────────────────────────────────────┐
 │ 级联 1: main() 应用层发起 xprintf("hello...") │
 └──────────────────────┬───────────────────────┘
                        ▼
 ┌──────────────────────────────────────────────┐
 │ 级联 2: xprintf() 参数打包，调用 xvprintf()     │
 └──────────────────────┬───────────────────────┘
                        ▼
 ┌──────────────────────────────────────────────┐
 │ 级联 3: xvprintf() 解析格式，单字符调用 xputc() │
 └──────────────────────┬───────────────────────┘
                        ▼
 ┌──────────────────────────────────────────────┐
 │ 级联 4: xputc() 从 RAM 读取指针路由到 uart_putc│
 └──────────────────────┬───────────────────────┘
                        ▼
 ┌──────────────────────────────────────────────┐
 │ 级联 5: uart_putc() 查询硬件状态，向物理地址    │
 │         0x3000000c 写入字符数据                 │
 └──────────────────────────────────────────────┘
```

### 极细分析：最终硬件发射动作（级联 5 详解）

当数据路由到最终驱动 **`uart_putc`** 时，反汇编（`0x7d4`）执行了最核心的硬件读写控制：

```assembly
000007d4 <uart_putc>:
  ...
  7ec:	300007b7          	lui	a5,0x30000
  7f0:	00478793          	addi	a5,a5,4       # a5 指向 0x30000004 (STATUS 寄存器)
  7f4:	0007a783          	lw	a5,0(a5)      # 读取 STATUS 的值
  7f8:	0017f793          	andi	a5,a5,1       # 取最低位 (tx_busy 忙闲标志)
  7fc:	fe0798e3          	bnez	a5,7ec        # 若忙，则自旋等待！
  
  800:	300007b7          	lui	a5,0x30000
  804:	00c78793          	addi	a5,a5,12      # a5 指向 0x3000000c (TXDATA 发送寄存器)
  808:	fef44703          	lbu	a4,-17(s0)    # 从栈帧中读出要发送的单个字节 (例如 'h' = 0x68)
  80c:	00e7a023          	sw	a4,0(a5)      # 【触发发送】写入物理寄存器
  ...
```

#### 1. 软件自旋查询（STATUS 状态）
*   **硬件表现**：串口控制器（UART Core）在发送前一个字符时，会将状态寄存器的最低位（`tx_busy`）拉为 `1`。
*   **软件行为**：CPU 通过 `lw` 指令不停地循环读取物理地址 `0x30000004`。一旦前一个字符发送彻底完毕，硬件自动将该位恢复为 `0`，CPU 结束自旋，准备写入新字符。

#### 2. 写入数据（TXDATA）与硬件移位输出（物理引脚行为）
当自旋通过，汇编执行 `sw a4, 0(a5)`，将字符（以 `'h'` 字符为例，十六进制 `0x68`，二进制 `01101000`）写入物理地址 **`0x3000000c`**：
*   **SoC 内部硬件动作**：
    1.  总线模块检测到对 `TXDATA` 寄存器的写周期。
    2.  串口控制器立刻将状态寄存器中的 `tx_busy` 自动拉高为 `1`。
    3.  硬件将 `0x68` 数据锁存到内部的 **并转串移位寄存器（Shift Register）** 中。
*   **外设引脚的电平动作**：
    1.  **起始位 (Start Bit)**：根据预设波特率分频计数，硬件串口控制器强制将物理输出引脚 `TX` 的电平拉为**低电平**（维持 1 个比特的传输周期），作为数据的开头。
    2.  **数据位 (Data Bits)**：移位寄存器受波特率发生器产生的传输时钟控制，从低位（LSB）到高位（MSB）逐位将数据推送至 `TX` 引脚上（**低电平、低电平、低电平、高电平、低电平、高电平、高电平、低电平**，分别对应二进制 `01101000` 的逆序输出）。
    3.  **停止位 (Stop Bit)**：8 位数据全部推送完毕后，硬件移位计数器触发，物理 `TX` 引脚强制恢复并保持为**高电平**（维持至少 1 个比特周期），标志这一个字节发送结束。
    4.  **硬件自动恢复**：物理引脚高电平输出后，硬件自动将 `tx_busy` 重置为 `0`，随时待命等待 CPU 下一次写入。

通过掌握上述从 C 代码底层调用、到编译指令映射、再到外设内部状态机与引脚物理电平的联合映射，您可以完美对照您的 Verilog 波形图（监测 `CTRL`、`STATUS`、`TXDATA` 寄存器及 `tx` 引脚波形），高效验证您自己编写的 RISC-V SoC 串口电路！

## 四、 补充说明：UART 外设地址的软硬件分配与适配指南

要让这套串口编译程序成功跑在您**自己设计的 RISC-V 处理器 SoC 上**，软硬件两端必须在**地址空间**上达成一致的默契。

### 1. 软件层面的地址规定
在 C 语言驱动中，外设的基地址和各寄存器偏移被严格定义在以下头文件中：
📂 **软件定义路径**：[tests/programs/common/include/uart.h](file:///d:/myProj_WJH/11_myRV/tests/programs/common/include/uart.h)

```c
#define UART0_BASE      (0x30000000)                // 物理基地址
#define UART0_CTRL      (UART0_BASE + (0x00))       // 控制寄存器偏移 0 字节
#define UART0_STATUS    (UART0_BASE + (0x04))       // 状态寄存器偏移 4 字节
#define UART0_BAUD      (UART0_BASE + (0x08))       // 波特率寄存器偏移 8 字节
#define UART0_TXDATA    (UART0_BASE + (0x0c))       // 发送寄存器偏移 12 字节
```
软件编译后，CPU 翻译出的所有访存指令（如 `sw`, `lw`），目标物理地址将直接落入 `0x30000000` 附近的区域。

### 2. 硬件层面的适配指南（如何在您的 SoC 上挂载串口）
如果您想在自己的 SoC 上运行这个编译文件，您的硬件设计必须按照如下原则进行适配：

#### (1) 总线译码器（Decoder）分配
在您设计的系统总线（无论是 Wishbone、AXI、AHB 还是自定义内部总线）的**总线互联矩阵（Interconnect/Decoder）**中，必须拥有一张**物理地址映射表（Address Map）**。
*   在这张地址映射表中，必须划出以 **`0x30000000`** 为起始地址的至少 `20 字节`（支持 5 个 32 位寄存器）的物理空间，全权交由您的串口控制器 IP（UART Controller IP）来响应。

#### (2) 外设片选（Select）与数据路由
*   **地址译码**：总线译码器必须实时监听 CPU 送出的访存地址 `Addr[31:0]`。一旦检测到地址的高位匹配上 **`0x30000000`** 前缀（例如监听 `Addr[31:28] == 4'b0011`）：
    *   译码器必须立刻拉高针对串口外设的**片选使能信号（如 `uart_sel` 或 `uart_req`）**。
    *   总线译码器需要将地址低位的偏移量（如 `Addr[4:0]`）路由至串口 IP，用于在其内部选择具体的硬件寄存器（如 `CTRL` 或 `TXDATA`）。
*   **数据通路**：将 CPU 的写数据线（`wdata`）和读数据线（`rdata`）挂接到串口控制器的物理接口上。

#### (3) 读写确认（Ready/Ack）响应
*   如果您的 SoC 采用的是具有握手机制的同步总线（如 Wishbone 或 AXI）：
    *   当 CPU 对 `0x30000000` 区间发起读写时，您的串口控制器硬件电路在完成本次读写周期后，**必须及时向总线反馈一个“确认/就绪（Ack/Ready）”信号**。
    *   如果没有这个就绪反馈，CPU 的总线访问将陷入无限期挂起状态，导致处理器流水线因等待外设响应而永久死锁。
