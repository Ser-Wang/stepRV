# RV32I 基础五级流水线：数据冒险与前递机制综合分析指南

在五级流水线 CPU 设计中，处理数据相关（Data Dependency）和控制相关（Control Dependency）是保证处理器正确运行的核心。为解决由这些相关性引起的冒险（Hazards），我们必须结合使用流水线停顿（Stalling/Interlocking）、气泡冲刷（Flushing）以及数据前递（Forwarding/Bypassing）技术。

本文档是对冒险检测机制与前递网络硬件映射位置的深度剖析，并解答了“前递控制信号的产生时机与位置”这一核心架构问题。

---

## 一、流水线模块职责：HDU 与 FU 的分离式设计

为保证逻辑清晰并严格遵循数字集成电路设计的最佳实践，我们通常将冒险处理的职能一分为二，拆分成两个专职的组合逻辑（或伴随少量流水线寄存器）子模块：
1. **冒险检测单元 (HDU, Hazard Detection Unit)**：专职负责“停顿与冲刷”。
2. **前递旁路单元 (FU, Forwarding Unit)**：专职负责“数据抄近道”。

这两者的作用机制、实施层级（流水段）截然不同。

### 1. 冒险检测单元 (Hazard Detection Unit)
* **执行层级（工作位置）**：**译码阶段（ID段）**
* **核心目标**：预防 Load-Use 冒险（访存后直接使用）等无法通过前递途径解决的数据重度依赖，或者处理控制冒险（分支预测判断）。
* **作用机制**：通过“看前顾后”的方式发号施令。
  * **输入**：提取当前位于 ID 阶段的指令所需的源寄存器索引 `$RS1_{ID}$` 与 `$RS2_{ID}$`；监听当前位于 EX阶段 正在执行的指令的目的寄存器索引 `$RD_{EX}$`，并检查该指令是否为 Load 指令（内存读取）。
  * **输出**：若发生冲突，证明所需的数据要等到下一个时钟周期后的 MEM 阶段才能给出结果，在时间上存在不可逾越的间隙。HDU 会立刻（作为纯组合逻辑）输出 `stall` 与 `bubble` 等控制信号。
  * **行为**：
    * **IF级被冻结**：令 `ifu` 停止取指（令PC及其流水线寄存器保持）。
    * **ID级被冻结**：令 `idu` 保存当前状态不更新。
    * **插入气泡**：向 ID/EX 流水线寄存器之间塞入 NOP 控制信号（将写使能 `wen`、数据请求全部置0），排空即将进入 EX 的这一个周期。

### 2. 前递控制单元 (Forwarding Unit)
* **执行层级（工作位置）**：**执行阶段（EX段）**
* **核心目标**：应对 ALU-ALU 或者 MEM-ALU 的轻微数据重度依赖。
* **作用机制**：
  * **输入**：拦截处于 EX 阶段将直接送往 ALU、LSU 或者 BRU 的硬件源操作数寄存器索引 `$RS1_{EX}$` 和 `$RS2_{EX}$`；横切并监听 MEM 阶段将要写回的 `$RD_{MEM}$` 以及 WB 阶段行将写回的 `$RD_{WB}$`。
  * **输出**：产生 `forward_a` 和 `forward_b` 选择控制信号（Mux Select），进而将最新鲜运算的数据“近端”绕道投送给 ALU。

## 二、架构释疑：前递MUX与控制信号究竟在哪产生？是否需要打拍？

一个十分深刻的问题是：“如果在译码级统筹全局进行危险检测，那前递多路选择器（MUX）的控制信号也是在ID计算好然后再跟着流水线打一拍发给EX吗？”

**权威解答：不是。前递的选择信号不需要打拍，而是必须在执行阶段（EX）中即席产生并立即消耗。**

### 为什么不能在 ID 级打拍传给 EX 级？
1. **数据与逻辑状态的时效性**：如果在 ID 级“预判”未来的前递动作并存入流水线寄存器，当时钟打拍推进后，万一遇到后续流水级（如MEM外部总线握手未完成）卡顿造成整体流水线 Stall，预先判断出的那个“前递 MUX 选择位”就可能因为生命周期的变化而出现超前失效。
2. **硬件时序复杂度剧增**：前递发生的前提通常是 EX 和后续流水级在当前时钟周期内的相对关系。在 ID 阶段强行远眺三个周期的结果来做静态标记，将导致该级控制器的组合逻辑层数成倍增长。

### 标准的前递设计实现方式
标准的 RISC-V 5级流水线前递是这样处理这些信号路径的：

1. **流水线传输索引（而非控制信号）**：在流水线寄存器（ID/EX 边界）中打拍保存的值必须是源寄存器的“标识索引”，也就是将 `rs1_idx`（5 bit）和 `rs2_idx`（5 bit）打拍传递给 EX 级模块。
2. **在 EX 即时生成控制信号**：`Forwarding Unit` 实质是个放置在 EX 级的组合逻辑判决块。它收集刚刚打拍送来的 `$RS1_{EX}$`（以及 `$RS2_{EX}$`），与当前时钟周期内身在 MEM 的 `$RD_{MEM}$` 和 WB 中将生效的 `$RD_{WB}$`，及其是否含有有效的写寄存器使能同时进行即席三元比对（含0号寄存器排除法等条件验证）。这不仅保证了前推选择是最实时的反映，并且确保一旦流水线挂起，旁路比对仍然稳如磐石。

## 三、代码架构对应：现有 de_rtl 的整改方案建议

为将理论付诸工程实践，结合当前工程进度，建议对 `./de_rtl/v0_rv32i_basic` 的架构作如下适配性整顿归置：

**1. 剥离并重构 `ctrl_hazard.v` 逻辑**
在此前临时将 `ctrl_hazard.v` 作为 EX 核心并包含算术行为的架构下，目前其中同时存在 `idu` 下放过来的未清理的部件模块例化。需要将运算行为回归正源（`exu.v`等专职算术层），令 `ctrl_hazard` 彻底蜕化为只有全局状态监听网络和组合逻辑输出的纯“监控室”，或者将其分离为两个小模块：

* **实例化 HDU:** 收集来自于 ID 层的寄存器数据需要反馈情况与地址，收集 EX 层的 load 动作标记。生成总的 `stall` 信号，送返 `ifu`, `idu`；生成 `flush` 信号以清除 EX 前的缓存动作。
* **实例化 FU:** 单纯对 EX 环境内的送入信息及外部 `mau`, `wbu` 进行逻辑运算。

**2. 安放 MUX 多路数据选择器**
将前递数据的MUX，必须放置在正在计算的模块内（也就是送入 `exu_alu.v` / `exu_lsu.v` / `exu_bru.v` 之前）。

在实际连线重构中，原来直接提取 `$RS1` / `$RS2` 的地方（形如 `wire [31:0] alu_rs1 = ... & rf_rs1_r_ex;` ），需要更换为类似如下带三元选择判断的前递挂载数据流路线：

```verilog
// 依据 FU 判断给出的即时控制信号，就地选择数据：
wire [31:0] forwarded_rs1 = 
    (forward_a == 2'b10) ? i_mema_wrbk_data :  // MEM -> EX 旁路前递
    (forward_a == 2'b01) ? i_wb_wrbk_data :    // WB -> EX 旁路前递
                           rf_rs1_r_ex;        // Default: 使用标准读取

// 原本直接连入 ALU / LSU / BRU 的线现接续挂在前递结果之下：
wire [`XWIDTH-1:0] alu_rs1 = {`XWIDTH{req_disp_alu}} & forwarded_rs1;
```

**3. 对流水线寄存器的扩充赋能**
* 返回你的 `idu.v` 文件，必须确保把正在调用的 `rs1` 与 `rs2` 地址（各 5-bit）接出到 ID/EX 流水线寄存器并持续向下拍送，使其能够成功送达 FU (位于 EX 级环境中)。

希望这份总结能够有效帮助你理清后续阶段中“处理数据冒险与旁路机制”在代码结构和寄存器布置中的全局脉络。
